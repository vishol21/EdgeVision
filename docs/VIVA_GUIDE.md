# Viva questions and defensible answers

These answers describe implemented behavior. Use [the evidence index](README.md#evidence-map) for supporting records; do not turn proposed work into completed features.

1. **What problem does EdgeVision study?** How cloud-only versus fog/edge placement affects modeled video-analytics workloads at different source demands, alongside actual local recording analysis.
2. **Does YOLO run inside iFogSim?** No. Python runs YOLO26n/ByteTrack locally; Java receives a finite workload profile and simulates processing demand/placement. Frames are not passed to iFogSim.
3. **What are the two technical components?** Actual local video analytics and discrete-event cloud/edge simulation. Synthetic camera sources can run independently of uploads; multiple uploaded recordings extend the local-analysis path.
4. **What is a virtual camera?** A distinct finite simulator sensor producing synthetic tuples. At the default timing, each emits 150 tuples over a 15-second arrival window; one to ten sources are supported.
5. **How do you know source count changes the workload?** Stage 2 inspected sensor identities and actual emission/count/timing telemetry at 1, 2, 3, 5, 6 and 10 cameras. Stage 7 repeats matched workloads, rather than changing a UI label alone.
6. **What does ByteTrack add?** Persistent track IDs and track histories within each recording, supporting configured activity rules. IDs are not guaranteed unique real-world people and are not reconciled across cameras.
7. **Which rules exist?** Restricted-area intrusion, loitering, wrong direction, crowd threshold and vehicle stopping. They are configurable rule triggers, not proof of crime/harm. Region-dependent rules need configured regions.
8. **What does zero reported events mean?** Only that no configured/evaluated rule emitted an event for that processing run. With empty regions, region-based rules are not evaluated; zero cannot prove safety.
9. **How is video connected to simulation?** A successful report supplies source timing, processed-frame counts and finite tuple batching. CPU MI/payload use declared configured estimates or Java assumptions when uncalibrated. Measured inference seconds are not automatically hardware-calibrated MI.
10. **How is a cloud/edge pair fair?** Both scenarios receive the same immutable profile/identity, counts, per-source timing and within-pair horizon; only placement differs under the existing model. Validation rejects mismatches/incomplete results.
11. **What is the topology?** One cloud and two identically configured fog/edge devices. Cloud placement hosts analyzer, detector and result storage in cloud; edge placement hosts analyzer/detector on fog devices while storage remains in cloud. This is a model, not physical deployment.
12. **What is the latency unit?** Raw CloudSim time units. Legacy JSON keys end in Ms without conversion; Stage 8 corrected presentation and documented compatibility, preserving values and saved jobs.
13. **Why report two latency metrics?** Full loop runs from emission to result arrival at cloud storage. Detector-arrival latency stops before detector computation and final delivery. Different endpoints can move in opposite directions; neither is measured physical capture-to-alert time.
14. **What is simulation runtime?** Java controller-region wall-clock duration, excluding video analysis, build/JVM startup and topology construction. External JVM elapsed time is separately retained. Neither equals simulated horizon or footage duration.
15. **What are network and energy values?** Counted modeled payload traffic (decimal MB) and configured device-model energy, not measured LAN traffic or power-meter readings. Headers/camera power are not fully represented. Longer horizons affect idle energy.
16. **What did the final evaluation show?** Eleven cases, five measured pairs each: 110 scenarios plus two excluded warm-ups. Edge reduced detector-arrival latency and traffic, but increased full-loop latency; recording-derived cases also used more modeled energy. See exact signed results rather than claiming universal superiority.
17. **Are repeats statistically significant?** No such claim. Deterministic modeled metrics repeated exactly; host runtime varied. Means, sample deviation and min/max are descriptive, not confidence intervals or proof of general validity.
18. **Were ten real cameras tested?** No. Synthetic sensors and replicated A/B recording profiles modeled ten logical sources. The two actual analyzed test clips were 160x120 moving-shape fixtures, not ten physical cameras or a representative CCTV accuracy dataset.
19. **How are multiple videos processed?** Sequentially, with independent job/camera IDs, reports and profiles. Successful sources combine without inventing common FPS; totals sum per-source counts and preserve independent intervals. Common simulated start does not establish synchronized capture.
20. **What happens on partial failure/restart?** Failed sources remain visible and excluded; all-failed batches run no simulation. Successful reports survive a later simulation failure. Explicit recovery validates persisted associations/counts/results. Unfinished jobs are not automatically resumed.
21. **Why do results disappear after refresh?** To prevent historical standalone results being mistaken for a new configuration. Files remain on disk; batch recovery is explicit, and single-job recovery is available through validated job APIs.
22. **Which reference paper was selected?** Yammanuru, Reddy, Jose and Rajagopal, Real-Time Video Analytics at the Edge: Enabling Low-Latency and Scalable Solutions, ICCCNP 2025, DOI 10.1109/ICCCNP63914.2025.11233420. Stage 6 reviewed its full supplied text and recorded conflicting configuration labels and incomplete reproduction details.
23. **Does this reproduce that paper?** No exact numerical replication. The paper describes YOLOv8n and proposed adaptive/priority allocation; EdgeVision uses local YOLO26n/ByteTrack and fixed mappings. Workloads/endpoints/parameters differ, and the paper itself leaves physical validation as future work.
24. **What is the project's contribution?** An inspectable local analytics-to-profile pipeline, multiple-recording identity/recovery and matched reproducible placement evidence under disclosed assumptions. It is not a demonstrated novel detector/scheduler or cross-paper superiority result.
25. **What remains for future work?** Permissioned labeled recordings, detector/event accuracy metrics, CPU/payload calibration and sensitivity, per-device energy attribution, physical edge trials and separately approved RTSP ingestion/reconnection. Do not claim privacy compliance, real-time 1080p capacity or production security without evidence.
